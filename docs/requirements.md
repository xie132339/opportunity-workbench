# 国内多平台捡漏与信息差工作台

返回 [[Start Here|Obsidian 首页]] · 编写结构参考 [[Templates/软件开发方案模板]]

> [!abstract] 选型结论
> 先用 **changedetection.io** 做网页监控底座，用 **RSSHub 和网站原生 RSS** 补充信息源，再以 **Python＋Flask＋Jinja2＋SQLite** 二开中文业务工作台。通过 API 连接监控底座，二开重点是渠道适配、同款识别、行情依据、成本核算、提醒和实际收益复盘。

> [!important] 范围与证据
> 本文保留完整产品需求和技术设计。截至 2026-10-02，源码开发版已运行，4 个平台的 8 个具体入口经过条目提取检查；这只证明当前入口可获取标题与链接。长期稳定性、可买价格、交易资格、真实收益及完整业务场景尚未验收。具体已完成与未完成范围见 [[多平台机会工作台-实施日志]]。金额示例仍仅用于说明。

## 用户场景与完成定义

### 用户目标与约束

面向个人使用和中国市场，从小资金、少量实际交易开始。用户业务经验较少，希望利用成熟项目和 AI 减少查找信息、整理条件和比较价格的时间，也希望底座能够继续二开。

**覆盖必须跨平台、跨信息类型。** 茅台、新款苹果手机只是信息差的例子；方案同时覆盖零售优惠、二手、供货清仓、拍卖、新品补货以及公开服务商机。不能把整个产品收缩成某一个平台的监控脚本。

完整使用流程：

**发现线索 → 核实条件 → 比较行情 → 算清成本 → 提醒用户 → 人工判断和执行 → 记录成交及实际收益。**

成功标准是用户能持续获得有来源依据的机会、了解限制与资金占用，并把机会关联到真实交易结果。软件能够运行、网页抓取成功、价格看起来便宜，分别只是其中一部分。

### 首版边界

首版提供单人中文工作台，支持自动来源与人工线索进入统一流程。人民币金额用整数“分”保存，数量和计价单位单独记录。交易由用户人工执行，系统保存决策和成交结果。

多平台是整体产品范围；首批自动入口按实际验证结果逐步上线。每个入口的自动化程度必须可见。分钟级定时监控适合普通机会发现；不能将该方案描述为已经具备秒级抢购能力。

## 现有系统接入点

### 底座与组件取舍

| 部分 | 选型 | 职责与复用范围 |
|---|---|---|
| 网页监控 | changedetection.io | 定时检查、页面变化、历史记录、价格与补货监控能力 |
| 信息订阅 | RSSHub＋网站原生 RSS | 获取已适配且当前可用的爆料、文章、公告和更新 |
| 业务工作台 | Python＋Flask＋Jinja2，少量 JavaScript | 中文界面、机会管理、商品匹配、利润计算与交易复盘 |
| 业务存储 | SQLite | 个人首版的配置、记录、任务进度和通知记录 |
| AI 分析 | 可配置的模型接口 | 提取条件、整理信息、辅助识别同款；按调用预算启用 |

动态网页需要浏览器时，接入 changedetection.io 支持的浏览器组件。工作台通过 API 连接底座；业务数据放在自己的数据库，避免依赖底座内部文件结构。

| 其他已讨论项目 | 当前安排 | 原因 |
|---|---|---|
| Huginn | 后续确有复杂编排需要时再评估 | 首版的监控、业务处理与提醒已有明确承担者 |
| Crawl4AI | 特定采集需求无法由现有方式满足时再接入 | 它提供采集能力，商品规则、利润和交易闭环仍由业务层负责 |
| Open Scouts | 作为产品交互参考，首版不采用其完整部署方案 | 官方方案依赖 Supabase、OpenAI、Firecrawl、Resend，增加国内使用条件下的接入与改造工作 |

来源：[changedetection.io 官方说明](https://github.com/dgtlmoon/changedetection.io)、[官方部署配置](https://github.com/dgtlmoon/changedetection.io/blob/master/docker-compose.yml)、[Huginn](https://github.com/huginn/huginn)、[Crawl4AI](https://github.com/unclecode/crawl4ai)、[Open Scouts 部署说明](https://github.com/firecrawl/open-scouts#readme)。

### 已核对的监控 API

| 工作台操作 | API |
|---|---|
| 新建监控 | `POST /api/v1/watch` |
| 修改配置 | `PUT /api/v1/watch/{uuid}` |
| 读取任务 | `GET /api/v1/watch/{uuid}` |
| 读取历史索引 | `GET /api/v1/watch/{uuid}/history` |
| 读取指定快照 | `GET /api/v1/watch/{uuid}/history/{timestamp}` |

工作台保存业务来源与监控 UUID 的映射。API 使用服务端凭据调用，凭据不暴露给页面前端。

“立即检查”会提交后台检查任务。界面先显示检查中，获得真正的新结果后再更新时间，不能以排队接口返回成功作为采集成功。

来源：[官方 API 文档](https://changedetection.io/docs/api_v1/index.html)、[Watch.py 实现](https://github.com/dgtlmoon/changedetection.io/blob/master/changedetectionio/api/Watch.py)。

## 最小架构与职责

```text
网页监控 ── changedetection.io ─┐
RSS / RSSHub ──────────────────┤
已获准使用的平台接口 ───────────┼→ 保存原始记录
人工录入 ──────────────────────┘        ↓
                                  提取统一字段
                                       ↓
                                去重、同款匹配
                                       ↓
                                条件筛选、成本核算
                                       ↓
                                机会中心、消息提醒
                                       ↓
                                人工核实、记录交易
                                       ↓
                                  实际收益复盘
```

业务部分保持一个代码项目，网页服务和后台处理进程共用代码与业务数据库。定时采集由对应入口的监控或获取模块承担，工作台负责消费记录、运行规则和发送业务提醒。

先在本机部署；需要全天候运行时迁移到常开主机。本机休眠、关机或断网期间不能持续采集。部署固定组件版本，保存数据库、配置及必要快照的备份。

## 必须覆盖的功能及逐项验收

### 渠道范围

下表是**候选接入范围**。平台名称代表需要研究的来源，不代表已经取得其接口权限或完成自动采集。

| 机会类别 | 候选渠道 | 重点字段 |
|---|---|---|
| 零售优惠 | 京东、淘宝天猫、拼多多、唯品会、品牌官网 | 规格、优惠条件、到手价、有效期 |
| 优惠线索 | 什么值得买、慢慢买、品牌活动公告 | 爆料、原始购买链接、限制条件 |
| 二手与闲置 | 闲鱼、转转、孔夫子旧书网、本地公开信息 | 型号、成色、附件、地域、报价 |
| 供货与清仓 | 1688、义乌购、供应商公开页面 | 起订量、阶梯价格、运费、交付条件 |
| 拍卖与资产处置 | 阿里拍卖、京东拍卖、公开资产处置公告 | 标的、报价、保证金、佣金、交付成本 |
| 新品与补货 | 品牌官网、授权渠道公告 | 发售与补货时间、限购、预售条件 |
| 服务与合作机会 | 公开采购、外包需求、招商信息 | 地域、资格、截止时间、服务要求 |
| 人工获得的线索 | 用户提供的链接、文字、供应商报价 | 来源、报价时间、备注、待核实条件 |

“支持平台”必须具体到入口、字段、频率和登录条件。例如支持一个公开公告栏目，不应被标为支持该平台全部商品。

RSSHub 已有值得买相关适配，但官方仓库也存在搜索失败并标记反爬的报告。有适配代码不能直接证明当前入口在中国网络下稳定可用。[适配目录](https://github.com/DIYgod/RSSHub/tree/master/lib/routes/smzdm) · [问题记录](https://github.com/DIYgod/RSSHub/issues/18938)

### 渠道管理需求

| 配置项 | 设计要求 |
|---|---|
| 来源身份 | 平台、入口名称、网址、机会类别 |
| 获取方式 | 网页监控、RSS、官方接口、人工录入 |
| 获取范围 | 指定商品、店铺、列表、关键词或公告栏目 |
| 运行配置 | 检查频率、有效时段、是否需要登录 |
| 运行状态 | 待验证、正常、需重新登录、暂时失败、已暂停 |
| 最近结果 | 最近成功时间、最近错误、实际获得的字段 |

采集失败要可见，不能把失败展示成“没有新机会”。需要登录、遇到验证码或字段无法获取时进入待处理状态，并继续支持人工录入。

### 五个主要页面

| 页面 | 功能 | 用户能完成的动作 |
|---|---|---|
| 机会中心 | 汇总全部渠道，按类别、平台、预算、时效筛选，展示详情和依据 | 查看原文、收藏、忽略、重新检查、补充信息、记录买入 |
| 渠道管理 | 新增来源、检查连接、设置频率、暂停、查看错误与登录状态 | 清楚哪些入口当前可用，恢复异常入口 |
| 筛选策略 | 品类、关键词、排除词、地域、预算、利润和通知条件 | 将个人偏好保存为可重复使用的规则 |
| 行情与对比 | 同款报价、成交依据、回收报价、人工参考价 | 判断价格是否可比、依据是否仍有效 |
| 交易与复盘 | 买入、费用、出售、退货、库存、实际收益 | 统计实际盈利和资金占用，识别有效渠道 |

机会详情必须回答：发现了什么、为什么值得看、需要多少钱、售价依据是什么、还有什么未确认、下一步怎么做。

### 同款与价格证据

同款比较至少包含品牌、型号、规格、版本、数量单位和成色。二手商品还要考虑维修、附件和保修。不同容量、整箱与单件、全新与维修机，不能直接合并计算差价。AI 提出匹配建议，关键规格不完整时标为待确认。

| 价格类型 | 使用规则 |
|---|---|
| 页面标价 | 保存为报价，不直接当作最终买入成本 |
| 优惠后价格 | 保存资格、有效期、叠加条件及是否已确认适用 |
| 别人的挂牌价 | 标明“挂牌参考”，不能冒充成交价 |
| 可核实成交记录 | 保存来源、时间、规格与成色条件 |
| 回收报价 | 保存有效期、验机和成色等适用条件 |
| 人工估价 | 明确为用户估计，可修改并保留更新时间 |

### 利润、资金占用与库存

```text
预估净利润
＝预估出售收入
－实际可获得的买入价格
－买入运费
－卖出运费
－平台及支付费用
－检测、维修、包装等成本
－其他适用成本
－风险预留
```

优惠资格不明时不能直接扣除优惠金额。关键成本缺失时显示“利润待核实”，未知费用不能当作零。

拍卖保证金单独记录为资金占用，最终是否形成成本按退还结果处理。批发商品记录起订量、计价单位和剩余库存。服务、招商等商机展示预算、资格与截止时间，证据不足时不生成确定的预估利润。

机会阶段的预估与交易后的实际收益分别保存。未售商品计入库存和资金占用，不能计为已实现利润；实际费用、退款与退货结果纳入交易记录。

### AI 与通知

AI 用于提取商品和机会信息、整理复杂条件、辅助匹配同款以及解释策略命中原因。关键结论必须关联原文或人工记录；未找到的信息标为未知。金额由程序计算。模型失败时基础监控、规则筛选和人工操作继续工作。

首版通知为站内提醒与邮件，后续按需求增加飞书、企业微信等渠道。每条提醒包含来源、发现时间、变化内容、预估收益依据、待核实条件和原始链接。

相同事件不反复提醒；显著价格变化、条件改变等更新可以重新触发。保存待发送、已发送和失败状态，失败可重试。

## 数据结构与状态流转

### 统一来源记录

所有适配器输出统一信息，字段缺失应明确表达：

| 字段组 | 内容 |
|---|---|
| 来源 | 平台、原始链接、来源条目 ID、原文记录 |
| 时间 | 发布时间、发现时间、最近成功核实时间、有效期 |
| 描述 | 机会类别、标题、商品规格、成色、地区 |
| 交易条件 | 价格、币种、数量单位、库存或供应状态、优惠条件 |
| 依据 | 字段对应的来源依据、人工补充、待核实内容 |

原文发布时间未知时保留未知，不用采集时间替代。

### 业务数据对象

| 对象 | 保存内容 |
|---|---|
| 渠道与策略 | 来源配置、检查方式、筛选规则、任务映射 |
| 原始记录 | 快照、采集时间、处理状态、内容指纹 |
| 商品与报价 | 标准规格、各来源报价、证据类型和有效期 |
| 机会 | 命中原因、成本计算、缺失信息、处理状态 |
| 交易及费用 | 买入、库存、出售、退款、各项实际支出 |
| 通知与后台任务 | 发送状态、重试次数、处理进度 |

### 状态语义

| 业务对象 | 状态或结果 | 必须区分的情况 |
|---|---|---|
| 渠道 | 待验证、正常、需重新登录、暂时失败、已暂停 | 失败不能伪装成无新内容 |
| 机会 | 待核实、条件已核实、已忽略、已失效等处理标记 | 已提醒不能代表用户已经交易 |
| 交易 | 买入、持有库存、出售、退款／退货及最终结算记录 | 预估利润、库存价值与实际收益分别记录 |
| 通知 | 待发送、已发送、失败 | 发送结果与采集结果分别记录 |

机会与交易通过关联 ID 连接；一条线索可以没有交易，一笔交易需要追溯到实际采用的依据。

## 安全边界与异常处理

| 场景 | 设计处理 |
|---|---|
| 首次采集 | 建立基线，历史内容可入库，不能全部当作刚出现的机会推送 |
| 变化通知遗漏或服务重启 | 定期同步历史记录，补取所有尚未处理的快照，恢复处理进度 |
| 重复事件 | 同一监控任务和同一快照只处理一次，避免重复机会和通知 |
| 重新检查 | 展示排队或检查中，收到实际结果后更新成功时间 |
| 登录过期、验证码、访问失败 | 清楚显示异常和最近成功时间，等待处理，保留人工录入入口 |
| 价格、库存或优惠过时 | 展示数据时效；不能把旧快照当成刚核实的结果 |
| 商品关键规格缺失 | 标记待确认，不直接纳入确定的同款价差 |
| AI 超时或调用失败 | 保留原始记录，基础规则与人工处理继续可用 |
| 通知失败 | 保存失败原因并重试，避免重复创建机会 |
| 凭据与原始内容 | 登录凭据不写日志、不发给模型；原始资料中的个人信息按必要范围保存 |
| 主机停机或休眠 | 标明监控中断，恢复后执行补漏；全天候运行需要常开主机 |

## 实施阶段与退出条件

### 二开模块划分

| 模块 | 具体开发内容 |
|---|---|
| 监控接入 | API 客户端、任务 UUID 映射、首次基线、历史补漏、运行状态同步 |
| 渠道适配 | RSS、可用平台接口、人工录入和后续特定平台适配，输出统一字段 |
| 机会处理 | 去重、商品匹配、条件核实、利润计算、解释与证据关联 |
| 工作台与通知 | 五个页面、策略设置、站内与邮件提醒、发送记录和重试 |
| 交易与复盘 | 买入、持有、出售、费用、退款、库存及来源收益统计 |

新增平台的开发路径：**确认可获取入口 → 获取数据 → 映射统一字段 → 设置频率和异常处理 → 在中国实际网络下验证 → 标记可用范围**。

缺少稳定自动获取方式的渠道先保留人工录入。是否增加专用采集组件，依据具体入口的问题决定。

### 实施顺序

| 阶段 | 工作范围 | 退出条件 |
|---|---|---|
| 第一阶段：验证渠道 | 部署底座；从至少三个平台、三类信息中验证 5—10 个具体入口；记录失败条件 | 明确可持续获取的字段、条件与人工补充范围 |
| 第二阶段：建立工作台 | 中文界面、渠道管理、统一记录、去重、筛选、提醒和人工录入 | 多平台机会在同一个入口可查看、可追溯、可处理 |
| 第三阶段：加入判断能力 | 同款匹配、行情依据、优惠资格、成本和利润计算、AI 整理 | 能解释机会为什么命中，关键缺失项可见 |
| 第四阶段：交易闭环 | 买入、库存、出售、退货、费用记录和来源统计 | 能记录实际交易并计算实际收益 |
| 第五阶段：扩大覆盖 | 根据实际使用结果增加入口、登录渠道和必要的采集能力 | 增加平台时复用原有工作台、数据规则和复盘能力 |

**完整第一版包含前四个阶段。** 第一阶段的“抓到网页”不能作为整个项目完成的依据。

各阶段按可观察结果推进，实际工期与费用待入口实测后估计，不根据项目星数推断开发成本。

## 已知风险、未决问题与参考来源

### 实施时必须继续确认

当前没有预设用户的资金预算、品类偏好或通知账号，这些作为可配置项。首批具体入口需要取得访问条件并验证；自动可获得的数据和人工补录的数据必须分别标注。

一些来源只能取得挂牌价，另一些需要人工补充成交或回收报价。证据不足的机会保留“待核实”状态，不能补造市场成交价。

AI 供应商、调用预算、常开主机配置和运行成本在实施时按可用条件确定。实际盈利需要由交易记录验证；本方案的价值首先是减少重复查找、整理和计算，并保留可复盘依据。
