# 多平台机会工作台产品概述与落地需求

本产品帮助个人自动发现有实际价格优势的商品，说明优惠条件、价格依据和有效时间，并提供商品直达链接。当前优先打通淘宝真实优惠数据，沿用现有本地工作台；采集、品类、比较和提醒规则保留跨平台扩展能力。

本文由用户提供的 AI 草稿《一、产品概述.docx》修订，保留日常采购、优惠发现、单位价比较、降价提醒和订阅管理等目标。新增数据取得条件、证据边界、动态配置、现有代码差距及验收方法。原文的“必接平台”“自动取得全部价格”“全自动准确判断”等表述不作为已实现能力。

**本次交付是产品文档修订，不代表数据接口已接通或核心业务已验收。** 文中的规则和参数是待实现、待真实数据校准的产品要求。实际完成情况以[核心验收台账](core-acceptance.md)和[执行记录](../.agent/execplans/opportunity-workbench.md)为准；已有[需求文档](requirements.md)保留历史沿革，其交易台账、强制多平台首发等旧规划不再作为当前开发要求。

## 一 产品目标与范围

### 1.1 产品形态与用户

当前产品为单人使用的中文 Web 工作台，支持桌面和手机浏览器自适应。继续使用 Python、Flask、Jinja2 和 SQLite，从源码运行；不为了本轮需求重建微信 H5、独立 App 或多用户系统。

主要场景是家庭采购、刚需补货和有计划地囤货。用户需要回答：买什么规格、总共付多少、需要什么资格、相对什么价格便宜、优惠何时结束、去哪里买。商品便宜不代表需要购买，结果应同时显示购买数量、预算和起购门槛。

原稿中的用户年龄、竞品月活、行业能力对比和市场规模没有提供可靠出处，不作为本产品的事实或投资依据。

### 1.2 当前交付与长期能力

| 层次 | 范围 | 完成条件 |
|---|---|---|
| 当前核心交付 | 淘宝优惠发现、商品与金额绑定、优惠条件解释、价格比较、商品直达 | 真实来源持续产生合格记录，并能用原始证据复核结果 |
| 通用设计 | 来源适配、类目与规格规则、价格口径、基准、通知均可配置 | 新品类复用判断流程，新平台复用数据契约；只为接口差异增加适配器 |
| 后续扩展 | 天猫、京东、拼多多及其他平台 | 每个具体入口取得可用条件并通过真实验收后启用 |
| 后续场景 | 二手、返现、积分、试用、餐饮和本地生活 | 使用各自的计价、资格、有效期规则，不混入普通实物现金价排序 |
| 可选触达 | QQ、微信、邮件等 | 有可用网关或平台能力，完成接收端实际投递验证后启用 |

淘宝与天猫分别标记；“淘宝优先”不等于把所有淘宝生态链接归为淘宝商品。纸品是已知验证场景，不应在代码中写死关键词、数量或价格。

平台不记录本人的买入、库存、出售、退款或实际收益，不自动下单或抢购。自用省钱不要求有转售记录；转售估算需要独立的退出价格和费用依据，缺失时不生成利润数字。

### 1.3 成功的定义

成功意味着持续给出用户能理解、能追溯的优惠结果，并证明至少部分结果低于明确的可比基准。渠道配置数、网页数量、抓取成功数和自动化测试通过数，都不能代替这一结果。

没有合格优惠时允许为空，但页面必须解释“未找到符合条件的优惠”还是“来源不可用、字段不足、任务尚未完成”。连续没有产出时必须处理数据链路，不能通过放入普通商品让页面看起来有数据。

## 二 原稿中需要纠正的关键假设

| 原稿内容 | 落地修订 | 原因 |
|---|---|---|
| 微信服务号加 H5 为首版必备 | 沿用单人工作台；微信是可选触达渠道 | 当前没有已验证的公众号资质、消息权限与用户授权链路 |
| 淘宝、京东、多多进宝同时必接 | 当前淘宝先形成业务闭环，其他平台按同一契约扩展 | 不能假定已有三家的接口权限和数据覆盖 |
| 大淘客必接，好单库、折淘客兜底 | 仅保留为需要单独评估的候选服务，不默认启用 | 与用户要求的一手证据、停用低可信第三方来源保持一致 |
| 单位价低于品类 P10 且同时是历史最低才提醒 | 分别建立“同款低价”“同类价格较低”“观测期新低”“优惠活动”规则 | 新商品没有历史时不能完全失去发现能力；几类结论的依据不同 |
| 新人、会员、地区价一律排除 | 保留优惠限制，按用户选择匹配或展示为条件优惠 | 用户明确关心这些资源；未知资格不能当已满足 |
| 库存少于 50 不推、券必须剩很多 | 明确缺货或领完则停用；数量未知单独显示，不伪造数量 | 公共页面不一定暴露剩余数量，库存数字也不是价格证据 |
| DSR 统一阈值 | 只用当前渠道实际返回且语义明确的店铺指标 | 指标名称、量纲与可用性需要分别验证 |
| 每次抓取就是一条独立基准样本 | 抓取记录可审计，统计按商品、卖家、条件和时间去重采样 | 重复抓取不能提高独立性或人为放大样本量 |
| 自动算阈值就无需维护 | 自动统计加可配置规则、异常诊断和版本回放 | 分类错误、选择偏差和缺失字段不会被统计自动消除 |
| 每天固定推送 3—8 条 | 有合格结果才推，数量上限与免打扰可配置 | 为完成数量目标推普通商品会偏离核心目标 |
| 30/90/180 天历史曲线即装即有 | 只显示实际观测范围、缺口与样本量 | 不能补造安装之前的价格 |
| “七大品类”表中实际只有五类 | 采用动态大类、小类和比较组 | 修复口径矛盾，避免以固定品类数量限制系统 |

### 2.1 对修订方案继续提出挑战

以下取舍同时约束前文及后续实现。需要前置条件的能力不能被写成默认可用；算法能编码与真实业务可交付分别判断。

| 编号与被挑战的要求 | 为什么目前不能照单实现 | 可执行替代方案 | 验证方法 |
|---|---|---|---|
| F01 无账号、无 API 凭据还要全淘宝一手优惠 | 当前没有证明存在满足这些条件的稳定发现入口；开发者接口仍有访问要求 | 保持一手来源约束，按官方公开活动/店铺入口 → 可正常访问的商品页验证发现链；授权接口作为有条件增量 | 必须从入口自动发现新商品并取得真实优惠；仅监控手工给定链接不能算发现通过 |
| F02 把能打开页面当作接通渠道 | 登录页、空壳页面和普通目录都可能返回成功 | 每个入口分开记录发现、报价、优惠、比较四项能力；标记具体失败阶段 | 原始响应与实际产出逐项对应，不能只有 HTTP 200 |
| F03 每条商品都必须拿到确定实付价 | 未知账号资格、收货地区与券领取结果时无法作出此保证 | 已有公开价格按公开价展示；规则完整时给条件测算；账户实付作为可选证据 | 不重复扣券；未知资格不写为已满足；运费未知不报完整到手价 |
| F04 所有记录必须有变体数字 ID | 页面可能明确唯一销售规格，却没有公开变体 ID | 接受两条身份路径：官方变体 ID，或商品 ID 加被价格明确绑定的完整唯一规格指纹 | 多规格起售价必须拒绝；单规格页面有明确证据可通过，不用猜 SKU |
| F05 三卖家/二十样本才能提供任何比较 | 会阻断小样本下本来成立的明确价差 | 一对一同款比价和相邻观察降价先可用；多卖家中位数和同类分布作为后续增强 | 两家同款报 20 元、25 元时可说相差 5 元；不能因此叫全市场最低 |
| F06 所有品类套 10%/20% 就能识别捡漏 | 品牌、单位、质量、单价级别和优惠频率不同，百分比没有统一市场含义 | 先提供来源充分的差额和降幅；按比较组设置提醒阈值，未校准品类不自动贴捡漏标签 | 参数变更回放同一批样本，列出新增误报/漏报及原因；示例参数不直接批量上线 |
| F07 必须有券余量、库存数量和店铺评分 | 字段缺失不等于售罄，也不能证明充足 | 明确失效就撤回；数量未知显示未知，仍允许保留有依据的公开优惠 | 缺券余量不能伪装成零；未证明可领的券不称可领取，不进入确定优惠后价 |
| F08 AI 能补齐缺少的规格和券规则 | 推断不会生成商品事实 | AI/OCR 可提取并回链原文；确定性规则验证，原文没有的字段维持缺失 | 每个参与金额计算的字段都有原文位置或接口路径；模型常识不入基准 |
| F09 自动寻找全部叠加组合才算最优惠 | 缺少优惠的互斥、顺序或适用规则时，枚举越多越容易算出假低价 | 先支持单商品直接降价、单券和已证明可叠加方案；在用户预算、数量上限内求最小成本 | 输出参与比较的方案集合和逐步金额，不能用未知组合击败已证实方案 |
| F10 微信/QQ 提醒必须和商品发现同时上线 | 当前没有证明账号/网关及投递能力可用 | 站内订阅提醒作为基础，外部通道按真实配置接入 | 有真实接收回执才标为通道可用；站内能看结果不冒充微信已送达 |
| F11 把未知数据全部隐藏就算修复 | 页面会更干净，但采集和解析缺陷依然存在 | 隔离保证展示正确，同时按失败量优先修复入口、规格和金额解析 | 同一真实失败样本修复前后能回放对比；不以列表条数变少作为成功 |
| F12 可追溯率达到 80% 就等于用户满意 | 可追溯的普通价没有省钱价值；只推荐一条也可产生虚高比例 | 同时看真实优惠产出、价差可复核和关注范围覆盖 | 无优惠、无价差、只命中极少关注范围时，核心验收仍不通过 |

### 2.2 当前选择与条件变化

当前采用“淘宝一手优惠发现与持续监控，加明确范围内的比价和提醒”。源码能力按通用配置开发，运行范围随已验证入口扩展。不会为了填充数据恢复已停用的第三方线报。

若公开入口能取得商品和规则，就走公开采集；若只有正常浏览器渲染能取得内容，就增加该页面的浏览器适配；若必须登录或持有接口凭据，记录为访问条件缺失。工具更换只能解决抓取方式问题，不能创造访问权限。用户以后提供访问条件时再启用相应能力，当前不把授权申请当作已经可用的方案。

若这些路径均未取得有效数据，应明确“淘宝自动发现当前不具备交付条件”，暂停依赖该数据的功能扩张，并给出已尝试入口及具体失败证据。用户提供链接的监控可以成为单独有用的能力，但不能被替换成原定自动发现目标的完成证明。

## 三 核心使用场景

| 场景 | 输入 | 自动处理与结果 | 关键限制 |
|---|---|---|---|
| 找便宜商品 | 关键词、品类、预算、可接受条件 | 查询已接入来源，解析商品与优惠，按可比价格排序 | 搜索必须说明覆盖入口、检查时间与失败入口 |
| 监控具体商品 | 淘宝商品链接和规格 | 记录该报价对象的时间序列，变化后重新校验 | 一个商品链接可能有多个 SKU，不能直接混成一条历史 |
| 新优惠券或活动 | 官方商品、店铺或活动信息 | 识别新增或变化的优惠，关联适用商品后计算方案 | 券面额大不等于到手便宜，活动入口不等于适用全部商品 |
| 查价决策 | 具体商品或规格 | 显示当前价格口径、历史观察和同款/同类参照 | “同款”和“同类”分开；无基准时只说明优惠，不宣称捡漏 |
| 新人或会员优惠 | 用户自选资格、地区及预算 | 展示与选择条件相符的方案和完整门槛 | 用户声明资格不等于账号已通过平台验证 |
| 补货提醒 | 已关注商品、已确认的缺货记录 | 识别缺货到可售的变化，再核价格和优惠 | 单纯再次抓取成功不算补货 |

用户主流程：**搜索或订阅 → 查看合格优惠 → 看价格依据和条件 → 直达商品/领取入口 → 在购物平台自行购买。** 不要求用户先记录实际付款，才开始商品发现和公开价格比较。

## 四 数据从哪里取得

### 4.1 淘宝来源路线

| 路线 | 能承担什么 | 前提和失败后的处理 | 当前文档结论 |
|---|---|---|---|
| 淘宝商品、店铺和官方活动公开页 | 发现商品、观察页面价格、获取公开优惠规则 | 必须实际可读；需要登录或只返回占位内容时记录阻塞 | 优先实测的直接来源，不能承诺匿名全站覆盖 |
| 淘宝官方联盟物料接口 | 在接口授权范围内发现推广商品与优惠字段 | 需要应用凭据和推广位；确认账号权限、接口版本和字段后再启用 | 已有本地连接器代码，真实数据接通尚未证明 |
| 用户主动提供的商品链接或可合法访问的页面 | 扩充监控对象，验证具体商品 | 输入链接仍须自动解析、保存来源并核对规格 | 补充入口，不等于自动发现能力已经完成 |
| 一方页面中的图片、嵌入数据或脚本渲染内容 | 在正文不足时补充字段 | 保留快照，OCR/模型结果必须回链、校验 | 作为解析手段，不能凭模型常识补价格 |
| 线报酷、逛丢等已拒绝来源 | 无当前生产职责 | 不自动恢复、不换名称重新导入 | 维持停用 |
| 大淘客等外部服务 | 可评估候选发现和成本 | 先确认授权、费用、字段来源与可回溯性，再由用户决定是否采用 | 不设为必接，不默认作为独立价格基准 |

官方文档中“不需要用户授权”不表示无需应用凭据。现有物料 API 的文档仍列出 AppKey、签名和推广位要求；接口价字段也没有承诺是当前用户的结算价。[淘宝官方接口文档](https://developer.alibaba.com/docs/api.htm?apiId=35896)

**无账号、无 API 凭据时，公开页面路线仍可研究和实测，但全站自动发现及个性化优惠可用性没有保证。** 若某入口无法提供商品身份与金额，先换可读的一方入口或解析方式；连续无业务产出时把该入口列为未接通，不能用同一批失败请求冒充持续采集。GitHub/Gitee 提供的是实现参考，不能把示例 JSON、公开密钥或旧优惠当作实时数据。

### 4.2 来源能力与状态

每个来源登记平台、入口类型、范围、访问方式、权限条件、支持字段、适配器版本、分页方式、成功时间及最近失败原因。来源数按独立入口统计；独立价格证据数按报价主体与内容来源统计，两者不互换。

来源运行状态采用：未配置、待验证、可运行、需登录、受限、临时失败、已暂停。另行统计每轮的读取条数、明确商品数、明确报价数、优惠数、可比数和低价数。

“网络请求成功且解析正常”与“产生有效报价”是两个指标。接口正常返回空列表属于无结果；验证码、解析格式变化、分页中断属于采集问题，不能都显示为零商品。

### 4.3 发现和监控分别验收

发现任务输入是配置的关键词、店铺或官方活动入口，输出此前未知的商品标识和原始链接；观察任务输入是已知商品，输出对应规格的新价格/优惠观察。两者共享商品和证据对象，分别统计成功率。每天反复访问同一批链接不算不断发现新优惠。

一方采集的实现顺序为：正常 HTTP 内容和页面已公开的结构化字段，接着普通浏览器渲染后的同页信息，再评估具备访问条件的官方接口。每一步保留真实输入输出。HTML 换成浏览器后取得的同一价格仍是一个来源，不能重复计算独立性。

每个新适配器必须实现边界清楚的“发现”和/或“观察”能力，按品类配置选择任务。没有发现能力的适配器不能配置成全站搜索。对登录、权限或页面契约变化导致的失败，只有访问条件、适配器或来源状态发生有效变化才重试对应路径；普通网络错误可按退避策略重试。

## 五 从原始内容到可展示商品

### 5.1 统一处理过程

```text
来源配置与任务
  → 原始响应或页面快照
  → 页面类型与访问状态识别
  → 商品链接和商品身份
  → 报价对应的规格、购买数量、金额和条件
  → 价格观察与优惠资源
  → 同款/同类分组和基准计算
  → 判定优惠、低价或资料不足
  → 搜索展示、订阅匹配和去重提醒
```

原始内容可以保存，保存成功不代表进入用户默认商品列表。普通标价可以成为基准观察材料；没有优惠或相对低价依据时，不进入默认优惠推荐。

### 5.2 展示层级与准入

| 层级 | 最低要求 | 展示位置 |
|---|---|---|
| 原始线索 | 来源、采集时间和可审计内容 | 来源诊断，默认商品列表不展示 |
| 明确报价 | 商品身份、由变体 ID 或明确绑定的唯一规格确定的报价对象、购买数量、非歧义金额、价格类型、来源和时效 | 商品查价及报价资料；不自动推荐 |
| 公开优惠 | 明确报价，加同商品绑定的有效优惠规则或价格变更证据 | 优惠结果，清楚注明“公开价”或“条件测算价” |
| 低价机会 | 明确报价，加可比基准及达到规则的价格优势 | 低价筛选与相应订阅；说明比较范围 |
| 捡漏候选 | 低价优势达到更严格门槛、关键条件完整、来源新鲜且异常低价复查完成 | 标为“捡漏候选”，不保证用户一定能成交 |
| 无效/过期 | 明确失效、商品错配、冲突未消除或超过时效 | 诊断与历史，不参与当前排序和提醒 |

“金额未提取”“金额口径待确认”的记录不能占据默认商品行，也不能用 0 元替代。金额为 0 必须有真正免费及必付成本证据，并进入独立免费资源类型；付邮、返后零元、抽奖和积分兑换不算现金零价商品。

缺失字段进入有终点的补采任务：待采集 → 采集中 → 已取得 / 字段未提供 / 解析失败 / 访问受限 / 已过期。失败保存原因与重试时间，达到可配置重试上限后等待来源恢复或适配器更新；不能永远显示“待商家核实”而没有下一动作。

### 5.3 可追溯证据

每条价格和条件必须关联原始快照、提取位置或字段路径、解析器版本、来源、商品链接、采集时间和内容哈希。原文发布时间未知就保留未知；当前商品页没有发布日期并不妨碍保存本次公开价观察，但只能写“采集于”，不能写“刚发布”。

多轴信息分别保存：商品匹配确定性、价格类型、条件完整度、时间新鲜度、来源独立性。任一关键轴缺失应限制对应结论，不能让一个综合分数掩盖规格错配。

同商品页重复抓取、同一商家经多个接口返回、正文相同的转载不计为多家价格。疑似重复保留可审计关联，不在归并过程中删除原始证据。

## 六 规格与单位价格

商品身份分为“平台商品”“具体变体”和“可比商品组”。同一个 item ID 不保证是同一个 SKU；不同店铺间的 SKU ID 也不保证可以直接关联。跨店同款需条码、型号及关键规格等一致证据；标题相似度仅用于找候选。

| 比较组示例 | 必要区分字段 | 可用单位 | 禁止混算的情形 |
|---|---|---|---|
| 抽纸 | 纸种、系列、层数、幅面/尺寸、每包抽数和包数 | 元/百抽；元/包作辅助 | 张数未知含义时不能当抽数；普通纸与保湿纸不默认同组 |
| 卷纸 | 有芯/无芯、纸种、净重和卷数、必要的层数 | 元/千克；元/卷作辅助 | 包装毛重当纸净重；不同净重只按卷比 |
| 湿巾 | 用途、片数、尺寸、配方或适用人群 | 元/片或百片 | 婴儿湿巾、湿厕纸、消毒湿巾混算 |
| 洗衣液等 | 产品类型、系列、净含量、浓缩/普通、包装 | 元/升或千克 | 无密度依据的质量体积互转；洗衣凝珠直接换算成升 |
| 大米与食用油 | 品种/类型、等级、净含量、包装和保质条件 | 元/千克或升 | 不同品种与临期状态混作同款 |
| 牛奶与酸奶 | 品类、系列、容量、箱数、常温/低温、保质条件 | 元/升 | 酸奶与纯奶，常温与冷链混作同款 |
| 纸尿裤 | 品牌系列、尺码、片数、拉拉裤/贴片 | 元/片 | 不同尺码、产品系列直接当同款 |

通用计算：`单位价 = 已确认的方案金额 ÷ 本方案有效数量`。商品小计单位价与含必付费用单位价分别命名；运费未知时不称完整到手成本。组合装分别拆成组成项；无法可靠分摊时仅保存组合总价。

金额以整数分保存，数量和换算用 Decimal 或精确比例，展示时再四舍五入。不能以展示成两位小数的单价倒算整单价或判断是否历史同价。

类目树和比较规则从管理页配置：大类 → 小类 → 比较组。配置必填规格、允许转换、价格类型、样本门槛、时效、折扣门槛及版本；新增规则后先回放预览影响再启用。不能给所有“纸”统一设置固定捡漏价格。

## 七 优惠与捡漏的判定规则

### 7.1 价格类型

| 类型 | 能说明什么 | 不代表什么 |
|---|---|---|
| 商品公开价 | 某时点、某页面环境下的明示报价 | 当前用户的支付金额 |
| 官方推广价 | 官方推广数据返回的价格 | 已验证对应全部 SKU 或当前用户资格 |
| 条件测算价 | 按有证据的适用条件算出的方案金额 | 该用户已领券或结算已成功 |
| 结算观察价 | 特定账号、地区、数量和时点的结算页面金额 | 所有人可买、未来价格不变 |
| 参考标价/划线价 | 商家显示的价格对照 | 同款常价或真实历史成交价 |

结算观察是可选的增强证据，不要求个人付款记录作为基础采集门槛。公开价之间可做公开价比较；结论必须保留“公开价”限定。未知用户资格时展示“符合条件时预计”，不展示“你可实付”。

### 7.2 优惠方案计算

结构化规则至少包括优惠 ID、绑定商品或活动范围、券额或折扣、门槛、参与数量、有效期、资格、领取状态、互斥/叠加规则、必要费用和证据来源。字段必须有明确的未知状态。

对于规则明确的一种方案：

```text
方案现金成本 = 商品小计 − 有证据且适用的减免 + 运费 + 其他必付费用
方案单位成本 = 方案现金成本 ÷ 本方案得到的有效数量
```

减免须按来源定义的先后顺序及门槛计算，保存每一步金额。已经含券的价格不能重复减券；优惠先后顺序未知时不能尝试所有排列并把最低值称为可用。

第一版支持单商品、明确数量、直接降价和单券，以及来源明确说明可叠加的简单规则。以后扩展有限数量的同店组合，枚举已确认可行的购买数量与优惠组合；设置最大件数、预算和组合上限。不存在适用证明的组合不参加最优方案计算。

“最优”限定为**已采集、条件明确且满足用户约束的方案中成本最低**。需要凑单时显示整单支出、额外商品与数量；不能只显示分摊低价。返现、积分与赠品单列，不默认折成现金扣除。

### 7.3 三种基准分别计算

| 基准 | 数据与去重口径 | 可得结论 |
|---|---|---|
| 同商品同店历史 | 同 SKU、数量和资格口径；按时间采样，保留观测空缺 | 相对本店已观测历史的降价/新低 |
| 同款当前参照 | 同款规格及相同价格口径；不同卖家去重，取新鲜报价 | 低于已覆盖卖家的同款参考价 |
| 同类价格分布 | 同比较组单位价；控制卖家和同款重复权重 | 在该采样范围同类中价格较低，不能称为同款最低 |

三家不同接口不等于三家独立卖家。同店五次观测只能支持历史，不能替代三个卖家的市场参照。淘宝阶段计算的是已覆盖淘宝范围内的基准，不称跨平台市场价。

采用中位数作为中心参考，样本足够时计算 P10/P25/P50/P75/P90，附样本量、卖家数、时间范围和覆盖条件。当前被判定商品不进入自己的对照样本；促销榜单样本应标为“促销样本”，不当作全市场常价。

IQR/MAD 用于发现可疑异常并触发复查，不能把所有极低值直接删除，否则会漏掉真正的优惠。样本不足或 MAD 为零时不强套异常算法。不同资格、预售、临期和大促情境分组保留，不能静默混入日常基准。

### 7.4 可执行判定

设当前同口径单位价为 `U`，可用基准为 `B`：

```text
低于基准比例 = (B − U) ÷ B
同数量参考差额 = (B − U) × 本方案有效数量
```

低价判定要求 `B > 0`，身份和比较组匹配，条件口径一致，证据在有效期内，样本达标，并同时满足该品类配置的比例与金额门槛。

| 输出结论 | 触发依据 | 不足时的结果 |
|---|---|---|
| 有优惠活动 | 明确活动规则或来源明示的前后价差 | 仅促销词或划线价不能升级为捡漏 |
| 同款价格较低 | 同款当前基准成立，达到低价门槛 | 缺卖家/规格/基准时只显示可证实优惠 |
| 同类价格较低 | 同比较组单位价格分布成立，达到配置分位或折扣门槛 | 比较组不完整则停止此类排序 |
| 观测期新低 | 历史覆盖合格，当前低于此前合格最小观察价 | 只有一个观察点时显示“开始记录” |
| 观测期持平最低 | 当前等于此前合格最小观察价 | 与已经通知过的同价不重复提醒 |
| 捡漏候选 | 可用基准成立且达到较严格门槛，关键条件完整，异常复查通过 | 降级为公开优惠、低价观察或资料不足 |
| 低于自定目标价 | 用户设置的同规格目标价格被触发 | 明示个人目标，不当作市场基准 |

历史新低与同类低价不强制同时成立。不同规则独立命中，但每条结论都需要自己的证据。降幅大小只能参与有效结果排序，不能让规格错误或失效优惠通过准入。

### 7.5 初始参数与冷启动

以下数值仅保留为**实验配置示例，不是所有品类的默认发布值**。三卖家和二十样本用于评估较广范围的统计参照，不阻断一对一比价、相邻观察降价和明确优惠展示。20%也不自动等于捡漏；真实回放后按比较组启用相应标签并保存版本。

| 参数 | 建议起点 | 约束 |
|---|---|---|
| 多卖家统计参照 | 至少 3 个可区分卖家 | 卖家独立性未知则不认定为完整市场参照 |
| 同类分位数 | 至少 20 个去重可比报价，且至少 3 个卖家 | 控制单卖家权重；样本多不自动证明市场有代表性 |
| 一般低价实验阈值 | 低于基准至少 10%，且同数量差额至少 2 元 | 两个门槛按比较组校准；未校准时可显示事实价差 |
| 捡漏候选实验阈值 | 低于基准至少 20%，且同数量差额至少 5 元 | 未校准比较组不自动启用此标签；还须通过证据、费用、有效期和异常复查条件 |
| 30 天观测期标签 | 采样计划覆盖整个窗口，计划槽成功率至少 80%，至少 15 个不同日期 | 未达到时只写实际观察范围与缺口；90/180 天按同样原则配置 |
| 普通价格观察 | 初始建议每 30—60 分钟 | 以平台允许频率、资源预算与入口实测为准 |
| 短时活动观察 | 初始建议每 5—15 分钟 | 不支持该频率的来源不许承诺分钟级提醒 |

没有足够基准时：继续采集一般公开报价构建参照，同时展示有明确优惠证据的商品，或触发用户自定目标价。不能用划线价、LLM 常识或编造的“品类正常价”启动基准。参数不能为了让空列表有数据而被悄悄降低。

30/90/180 天均应写“已观测样本最低”，不保证捕获窗口内每一次短时波动；新用户安装当天只能看到已有合法来源覆盖的历史或安装后积累的数据。

### 7.6 不等待大样本也可以交付的结果

| 当前实际具备的证据 | 可直接提供的价值 | 必须限制的表述 |
|---|---|---|
| 一份绑定具体商品的有效优惠规则 | 展示优惠内容、参与方式和领取入口，规则允许时计算方案 | 不保证用户已领到，不宣称市场低价 |
| 同商品、同规格、同条件的前后两次有效观察 | 显示相对上一次观察的降价金额与比例，按订阅阈值提醒 | 只写两次实际时间，不叫 30 天历史最低 |
| 两个卖家同款、同规格、同费用口径的新鲜报价 | 显示两家价格及差额，可跳到更低的一家 | 只说“比已查另一家低”，不叫市场中位数或全网最低 |
| 已覆盖一段时间的合格价格序列 | 显示实际观察区间最低、样本数和缺口 | 区间有空缺时不能写成全时段捕获 |
| 达到配置覆盖要求的同类样本 | 提供同组单位价排序和分位参考 | 保留质量属性和样本范围，不声称跨品类等价 |

前两次观察不能都是重复读取同一旧快照；跨时点比较也要同口径。两家报价的商品小计可比较，但运费未知时只能描述商品小计差额。补齐运费后才能声称总成本节省，不能用备注里的未知运费抵消主标题的“省钱”承诺。

如商品原文写出优惠但条件未全，保留优惠说明及已确认公开价。只有缺失条件不影响该项公开价事实时才展示此价；不得以未核券抵扣。这样缺失数据限制相应结论，不把整条商品都锁进“待核实”。

## 八 页面与用户操作

| 页面 | 关键内容与动作 | 产品约束 |
|---|---|---|
| 商品搜索与优惠中心 | 搜索、筛选、默认列表、可切卡片、价格/单位价/时间表头排序 | 浏览器记住布局；价格缺失的线索不占商品列表；不同计价口径不混排 |
| 商品详情 | 具体规格、数量、方案总价、价格类型、券和活动、基准、时间、直达操作 | 首屏先给购买判断信息；原文、解析过程和诊断折叠 |
| 品类与基准管理 | 类目、必填规格、单位、样本、阈值、时效、规则版本及预览 | 无效配置不发布；已保存不等于重新计算完毕 |
| 渠道管理 | 入口能力、最近成功、失败原因、各阶段产出，启停/频率/批量更新 | 启用不等于接通，接通不等于有合格优惠 |
| 订阅与通知 | 品类/关键词/商品订阅、目标价、资格偏好、免打扰、发送状态 | 单人设置先复用现有策略；QQ/微信等按实际接入状态显示 |

列表核心字段：商品与规格、方案金额及价格类型、可比单位价、购买平台、优惠要点、低价依据、检查时间、操作。标题与长字段省略，完整信息在悬停或详情查看；操作列独立保留“详情”“商品直达”，来源证据入口与购买入口明确区分。

用户点击商品详情先展示数据库中的最近结果，实时复核在后台执行并显示进度，不把外部网站访问串到首次页面加载上。页面性能预算由真实机器基线确定，并记录列表/详情的中位和 P95 延迟；本轮文档不宣称性能已优化。

空结果显示查询条件、实际覆盖、最近成功时间和失败阶段。例如“本次检查 3 个入口，1 个受限，取得 18 个商品，5 个明确报价，0 个满足低价规则”，这些数字必须来自本次任务；可以由此进入诊断或调整条件，不能虚构商品占位。

## 九 数据结构与代码职责

### 9.1 复用已有系统

已有 `sources`、`events`、`opportunities`、`quotes`、`benchmark_categories`、优惠资源、通知及规则审计结构。第一步是明确这些对象的职责与准入，按必要差异增量迁移，不把原稿七张表直接建成第二套业务库。

| 逻辑对象 | 关键字段/约束 | 与现有代码关系 |
|---|---|---|
| 来源与采集任务 | 入口范围、访问条件、适配器版本、时效、结果计数、失败原因 | 复用 `sources` 和采集任务；能力字段按缺口补充 |
| 原始证据 | 内容哈希、快照位置、来源 URL、采集时间、字段路径 | 复用 `events` 等记录；原文与解析结果分离 |
| 商品与规格 | 平台 item ID、变体标识、卖家、规格、比较组 | 必要时增量规范化；ID 类型以平台契约为准，不硬限所有平台为纯数字 |
| 价格观察 | 商品变体、数量、金额、价格类型、条件签名、来源、采集时间、有效期、证据 ID | 对齐 `quotes` 和既有观察结构；不能拿机会行数当报价样本数 |
| 优惠与方案 | 券/活动 ID、范围、门槛、有效期、资格、互斥、计算步骤 | 复用优惠资源及商品关联；一个商品可以有多个方案 |
| 基准与决策 | 比较组、样本 ID、独立卖家数、覆盖窗口、统计值、规则版本、命中理由 | 扩展既有基准功能；可还原每一次结论 |
| 订阅与投递 | 用户关注条件、商品/方案指纹、发送状态、幂等键 | 单人阶段复用策略和通知结构；不先建设多租户用户中心 |

公开价、条件测算价和结算观察价分列，不能反复覆盖 `current_price` 导致价格类型丢失。`NULL` 表示未知；0 表示已经有证据的零值。库存使用可售、缺货、未知等状态，数量独立可空。

同任务重试按响应指纹/任务标识幂等；不同时间的相同价格可复用内容快照但保留观察时间。历史统计可以取小时/每日代表样本，不能为采样覆盖或删除原始事实。规则版本变化后能按保留证据回放。

### 9.3 更新与保留策略

采集频率、价格 TTL、优惠结束时间分别配置。成功访问来源首页不能刷新所有商品的核验时间；同条商品确实被重新观察后才更新其观测时效。明确活动结束优先于通用 TTL。

原始快照、价格观察和诊断日志采用不同保留期。目标展示 180 天历史，就必须保留足够的可审计观察数据；若清理导致证据不足，应撤销对应历史结论。优先做内容去重和冷归档；物理删除要预览影响、备份并依照授权执行。本次文档修订不清库。

#### S01 接通真实淘宝发现来源

**针对问题：** 页面能访问却没有真实优惠；手动提供链接的监控被误称为自动发现。

**具体实施：** 建立具体入口的能力记录，逐一处理淘宝官方活动、店铺或其他可读的一方发现入口。先读正常公开内容，再对确有渲染需求的页面使用普通浏览器适配；已有合法凭据时再接对应官方接口。关键词、类目、分页和频率从配置读取，代码中不固定纸品或固定商品。每轮分别记录发现的新商品、可用报价、优惠和失败原因。

**改动位置：** `scanner.py`、平台适配服务、`routes/sources.py`。来源资格和字段契约校验留在适配器，统计口径统一。

**交付与验收：** 从配置入口自动取得此前未知的真实商品，保存来源快照、商品直达链接、报价与优惠字段；正常后台周期能再次观察，过程不依赖用户逐条抄链接。入口正常无优惠、登录受限、格式变化、分页中断必须能区分。只有普通目录、HTTP 200 或接口示例不通过。

**失败处理：** 根据访问失败、无商品标识、无价格或无优惠分别处理；换方式须针对具体原因。不恢复已停用的线报源，不使用示例数据填充。如果所有可用一方路径都缺少访问条件，明确交付阻塞及已尝试证据，不承诺全淘宝覆盖。

#### S02 修复适配器的误拒绝和状态错误

**针对问题：** 有金额和优惠却被解析器丢弃，库存为零与未知混淆。

**具体实施：** 在 `services/taobao_alliance.py` 按字段用途拆分校验：参考标价仅在计算对应价差时必需，不作为所有优惠记录的统一必填项；数值 `0`、字符串 `"0"`、空值分别解析。优惠日期保留时间精度，按实际接口契约处理日期型和时间型字段。将带券搜索作为配置，规范化淘宝/天猫筛选参数，复核当前可用 API 版本及真实响应结构。

**交付与验收：** 回放有完整单券方案但无参考标价、券量为 0、券量缺失、日期型有效期、已过期、缺少关键条件等用例。合法候选不因无关字段缺失被丢弃；已领完不能标未知，未知不能标可领。模拟响应只证明解析分支；真实输入通过另行记录。

**失败处理：** 保留原始值和字段路径；接口不提供的数据转为明确未知，不凭经验填值。日期结束边界未明确时，限制时间敏感结论，不能擅自延长优惠有效期。

#### S03 把价格绑定到规格和购买数量

**针对问题：** 商品最低展示价、单包价、整单价和多规格报价互相混用。

**具体实施：** 使用商品 ID 加变体 ID，或者商品 ID 加被报价明确绑定的唯一完整规格确定报价对象。区分购买几件、每件有几包、每包多少抽/克/毫升；按品类配置单位转换。商品标题仅用于召回，不能单凭相似标题确认同款。保存提取依据，允许 AI 提出候选字段，但每个关键值都必须回链原文并通过校验。

**改动位置：** `services/marketplace_identity.py`、`offer.py`、`services/merchant_product_page.py`、`services/category_comparison_rules.py`。

**交付与验收：** 页面多规格起售价不得绑定到用户目标规格；唯一规格的真实页面即使缺少公开变体 ID 也能建立有依据的报价对象。抽/张、净重/毛重、单件/整箱、组合装均有反例。明确整单金额和数量才能换算单位价。

**失败处理：** 缺规格进入定向补采；无法区分的组合报价保留总价说明但不做同款比较。定位高频失败模式修解析，不让“金额未提取”长期占据默认商品列表。

#### S04 计算有依据的优惠方案

**针对问题：** 只看券面额、重复扣券、凑单只显示均摊低价，以及要求每条数据都有个人实付证据。

**具体实施：** 将券/活动关联到 S03 的报价对象，结构化门槛、减额、资格、有效期、件数、领取状态、互斥/叠加与运费。先实现直接降价、单券及明确可叠加的简单方案；在明确数量和预算内比较可行方案。方案分别保存公开价、条件测算价和可选的结算观察价。

**改动位置：** `benefits.py`、`offer.py`、商品优惠关联服务及 `services/product_search.py`。

**交付与验收：** 满 99 减 20 对 49 元单件不扣减；已含券价格不再减券；两件达门槛时显示两件总支出。新人/会员条件未知时不能称用户可实付，运费未知不能称完整到手总成本。每一步金额可由原始证据复算。

**失败处理：** 条件不全则保留已确认公开价和优惠说明，停算受缺失字段影响的优惠后价格。方案搜索不加入未知叠加组合，不把最低的假设价格当作最优。

#### S05 积累有效价格观察并处理时效

**针对问题：** 没有历史却显示历史最低；重复采集撑大样本；过期价格仍参与推荐。

**具体实施：** 为同商品、同规格、同条件的报价保存金额、观察时间、来源、原始证据和规则版本。同任务重试幂等；不同时间的真实观察保留时间信息，内容快照可去重。来源检查成功只更新确实观察到的商品。价格 TTL、券有效期、账号/地区条件分别管理；失效后撤销相关结果并标明原因。

**改动位置：** `db.py`、既有价格观察逻辑、`services/source_freshness.py` 和 worker 调度。迁移只增量演进，先验证兼容，不清除原始历史。

**交付与验收：** 重试不产生重复观察；重启后可恢复进度；重复读旧快照不伪造新核验时间；优惠过期后退出当前推荐。历史曲线只显示实际记录范围及空缺，安装一天不展示虚构的 90 天历史。

**失败处理：** 采集失败不能刷新商品时效。失败队列按原因和退避策略恢复；只有仍在 TTL 内的证据可继续参与当前比较。

#### S06 交付一对一比价和相邻观察降价

**针对问题：** 等待三家卖家或大量历史样本导致没有任何可用比较。

**具体实施：** 新增两类独立规则：同款同口径的 A/B 当前报价差额；同商品前后两次有效观察的降价。计算金额差、比例、比较时间与条件，保存参与计算的证据 ID。商品小计与含费总成本分别比较，不混淆价格类型。先让明确的事实价差可用，再接更广范围统计。

**改动位置：** `comparison.py`、`services/opportunity_analysis.py` 与搜索结果组装；不只解除参考价开关报错。

**交付与验收：** 同款 A 店 20 元、B 店 25 元可显示相差 5 元和相对 B 低 20%；不同规格禁止比较。当前 20 元、上次 25 元可显示“较上次观察降 5 元”，不能写“30 天最低”。同一卖家的多个入口不当多家。

**失败处理：** 可比条件不足只停用该比较结论，已证实的商品优惠仍可展示。只有一家且无旧观察时不编造基准。

#### S07 配置品类阈值并逐步启用统计标签

**针对问题：** 所有品类套固定低价线，或者为了让页面有数据任意放宽规则。

**具体实施：** 复用 `/price-benchmarks` 管理大类、小类、比较组、必填规格、计价单位、时间范围、提醒差额和降幅。规则保存版本和变更预览。样本达标后计算去重的多卖家中位数、同组分位数；当前待判商品从自己的对照集合中排除。原文中的 10%/20% 等只作校准候选，不自动应用于所有品类。

**改动位置：** `services/category_policy.py`、`services/category_comparison_rules.py`、`routes/price_benchmarks.py` 及独立的基准计算业务模块。

**交付与验收：** 新增一个品类无需复制搜索与金额算法；更新规则能预览真实样本的命中变化。没有合格样本的比较组不发布“捡漏”标签；已有一对一比较保持可用。极低价先核验，不能因低于统计范围就自动删除。

**失败处理：** 无样本时继续积累、展示事实价差或自定目标价；无法可靠归组的品类暂不启用同类分布。规则错误可恢复上一版本，并重算受影响结果。

#### S08 商品搜索展示真实可用结果

**针对问题：** 列表被普通价和缺金额记录占满，内容冗杂、操作重叠、详情等待外部网络。

**具体实施：** 统一搜索准入：明确报价用于查价；有效优惠或有依据的价格优势用于默认优惠结果。线索诊断保留独立入口。默认列表、卡片切换并记忆选择；表头排序只比较同口径数字。操作列固定“详情、商品直达”，长文字省略；详情先读当前数据库结果，后台复核单独显示进度。

**改动位置：** `services/product_search.py`、`routes/search.py`、`routes/opportunities.py`、相关模板与 `static/style.css`，复用已有布局避免无必要重做。

**交付与验收：** 普通目录价、歧义金额不会被标成优惠；搜索关键词、筛选、分页及排序可同时使用；手机与桌面操作不重叠。点击直达正确商品；详情不因来源访问超时而长时间无页面。空列表能区分采集失败和本期没有合格结果，并显示真实阶段计数。

**失败处理：** 展示问题回到对应报价、身份或方案处理修复；不以更换文案代替解析修复，也不以放宽准入制造商品数量。

#### S09 接订阅提醒与可用消息通道

**针对问题：** 外部账号未接通阻断首版，或同一条优惠重复发送。

**具体实施：** 复用策略保存品类、关键词、商品、目标价、资格偏好、提醒时段和数量上限。先实现站内通知；按实际配置逐个接 QQ/微信/邮件。按商品变体、方案、事件类型和接收端生成幂等键，推送前复查有效期；新降价、条件变化和补货按独立事件处理。

**改动位置：** 策略与通知路由、`services/alert_dispatch.py`、现有通知/投递表。

**交付与验收：** 一次有效变化只产生一次相应提醒；过期事件不发送；失败可重试且不重复创建。外部通道有接收端实际验证才标可用。首次历史导入不批量当新优惠推送，没有合格结果不凑条数。

**失败处理：** 网关未配置显示未接入，不阻断站内结果；发送失败和优惠数据失效分别处理。未经配置和授权不向外部账号发送测试消息。

#### S10 用真实链路完成业务验收

**针对问题：** 代码测试通过却没有可用优惠，或者只报可复核率掩盖数据覆盖不足。

**具体实施：** 为每个已实现步骤保留针对性回放与失败用例，最终由真实入口驱动“发现 → 报价/规格 → 优惠方案 → 观察/比较 → 搜索 → 提醒”。按用户关注范围固定验收范围，记录取得与未取得的数据；说明普通价、条件价、有效优惠和有比较依据的低价各有多少，不把它们相加冒充捡漏数量。

**交付与验收：** 形成一次可复查的真实业务结果及后台持续更新证据，覆盖过期、变价、错规格、源受限和重启等场景。报告优惠产出、字段完整度、推荐可复核率、关注范围覆盖和发现延迟；模拟响应与真实采集分开。任何关键字段伪造、错 SKU、重复扣券都需回到对应步骤修复，不能用平均分抵消。

**失败处理：** 按 S01—S09 定位未通过环节并记录下一动作。S01 没有真实发现，整体自动发现不能通过；S06 无基准，只能交付已证实优惠；外部通道未接通，只能声明站内提醒通过。没有真实商品结果，不能将空集记为 100% 成功。

## 十一 验收方法与指标

### 11.1 验证分层

原始真实快照回放用于验证解析和公式；实时来源读取用于验证入口仍可用；后台连续执行用于验证更新与过期；页面与通知验证用户能否理解和使用结果。模拟响应只覆盖代码分支，不能证明取得真实优惠。

每条验收记录包含来源、采集时间、适用范围、商品/变体、价格与优惠字段、实际输出、期望输出、规则版本及未验证项。首次开发验收可进行人工抽样复查，日常运行不依赖用户逐条人工核价。

| 用例 | 预期结果 |
|---|---|
| 普通商品标价，无优惠也无有效比较优势 | 可作报价参照，不进入默认优惠推荐 |
| 商家划线价远高于现价 | 可以描述来源促销，不能据此认定市场低价 |
| 原文有明确总价和规格但解析失败 | 记录字段路径和失败原因，修适配器后回放成功；不得仅换一条“待核实”文案 |
| 商品页多规格起售价 | 未绑定具体变体前不得与目标 SKU 比价 |
| 单品价、整单价和单包价混杂 | 必须还原购买方案；不确定时隔离，不能任选最低金额 |
| 同商品三次采集或三个转载入口 | 不计为三家独立报价 |
| 新人/会员价且用户资格未知 | 展示条件优惠，不能推送无条件可买结论 |
| 满 99 减 20，但买一件仅 49 | 不扣减；若有合法凑单方案展示全部支出和额外商品 |
| 接口已返回券后金额 | 不重复减券 |
| 日期只有年月日或接口改为新版格式 | 按已确认字段精度处理，不静默丢弃或臆造结束时刻 |
| 券库存未提供与明确为零 | 前者未知，后者已领完；处理不同 |
| 已取得新价格但旧观察仍在缓存 | 新结论绑定新证据版本，过期页面结果撤回或刷新 |
| 安装一天查看 90 天历史 | 只显示真实一天及缺口，不伪造曲线 |
| 极低价触发异常检测 | 先复查商品、数量和优惠，再决定保留或隔离 |
| 未知运费、积分或返现 | 不当零费、不直接折现金；不声称完整实付成本 |
| 所有来源失败或全部无有效数据 | 报告阻塞/无合格结果，不能以空集合声称全通过 |

### 11.2 人工可复算的规则示例

以下为**演算示例，不是实时商品或已采集数据**。假设同规格抽纸 100 抽×20 包，方案原小计 49.90 元，有明确适用且可计算的 15 元券、包邮，无其他必付费用：

```text
方案金额 = 49.90 − 15.00 = 34.90 元
总抽数 = 100 × 20 = 2000 抽
单位价 = 34.90 ÷ (2000 ÷ 100) = 1.745 元/百抽
若有效同口径基准 = 2.20 元/百抽：
同数量参考金额 = 2.20 × 20 = 44.00 元
参考差额 = 44.00 − 34.90 = 9.10 元
低于基准比例 = 9.10 ÷ 44.00 ≈ 20.68%
```

只有基准成立、商品与优惠绑定、费用及条件完整、时效合格、异常复查通过后，才可触发示例中的捡漏候选门槛。优惠只存在于宣传文案、资格未知或券未证明适用时，34.90 元最多是条件测算值，不能因为算术正确就说核价完成。

反例：同一券实际要求满 99 元，49.90 元单件不满足。两件小计 99.80 元，若规则确认可用则整单 84.80 元，40 包的单包均摊为 2.12 元；不能显示“单件实付 34.90 元”。

### 11.3 业务验收指标

| 指标 | 计算与意义 |
|---|---|
| 来源业务产出率 | 本期产生合格商品报价的启用入口数 / 本期计划执行入口数；附未配置、失败和无结果分布 |
| 报价完整率 | 具备身份、规格、数量、金额、口径、来源与时间的报价数 / 本期采集到的商品候选数 |
| 优惠公式可复算率 | 可从证据复算价格的优惠方案数 / 本期含价格主张的优惠候选数；过期、失败和字段缺失不静默移出分母 |
| 同款准确率 | 被判定同款的核查样本中匹配正确的数量与比例；另报未能复查数量 |
| 新鲜度覆盖 | 仍在字段 TTL 和优惠有效期内的当前展示报价数 / 全部当前展示报价数 |
| 基准覆盖率 | 存在合格基准的报价对象数 / 本期可比较的报价对象数；无基准的数量同步公布 |
| 推荐可复核率 | 验收样本中价格、规格、优惠和结论均有对应证据的数量 / 选定推荐样本总数；无法复查计未通过 |
| 真正业务产出 | 按品类统计合格优惠数、低价数、过期撤回数和发现延迟；不能只报采集总量 |

用户期望的“80%以上”不能被单一可复核率替代：可复核率只是必要指标，真实优惠产出和关注范围覆盖也须达到双方明确的目标。细化后的执行标准见 AC-S10-04/05：默认展示结果的身份、金额、公式和时效不得有已知关键错误；80%用于固定真实快照语料中可证明机会的召回目标，同时公开分母、失败原因及范围，不作为推荐安全性或全市场覆盖的及格分。零推荐不是 100% 正确，小量样本通过也不能外推全淘宝。错 SKU、已知过期、凭空价格、重复扣券等关键错误不能靠平均分抵消，应暂停受影响规则并修复。

日活、留存、点击率和每天几条推送不作为当前单人版的交付门槛。原稿的运营指标待确有多用户产品和数据后再设置。

## 十二 提醒与运行成本

站内结果和已有通知结构优先。外部渠道只有配置并实际验证后才标记可用；QQ 接入协议不等于已具备 QQ 网关，微信服务号也不等于可以任意主动群发优惠信息。

微信作为后续可选能力，需要核对账号条件、消息模板适用场景、用户授权和当前发送规则。本轮未能读取微信官方文档正文，因此不写固定配额或宣称已具备消息权限。[微信订阅通知文档入口](https://developers.weixin.qq.com/doc/offiaccount/Subscription_Messages/intro.html)

提醒以商品变体、方案、命中规则和接收端形成幂等键；低价显著变化、优惠条件变化或有效补货可以再次通知。发送前重新检查时效和关键状态，发送失败单独记录。首次导入历史不批量当作新优惠提醒。

现阶段继续本机源码运行。Python 依赖和本地数据存储不需要另买商业服务；外部 API 资格、可能的服务套餐、云主机、公众号能力、模型调用和通知费用分别核对，不承诺全链路免费。LLM 为可选的候选提取工具；主要金额计算、规则判断和通知调度应可独立运行。

当前版本不实施转售盈利判断、跨店复杂凑单、账号个性化实付保证、自动抢购或“全网最低”。这些能力保留研究入口，但不能进入当前开发依赖。新增品类与更清楚的报价展示仍服务于同一省钱目标，不需要等这些扩展功能。
