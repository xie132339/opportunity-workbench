## 对当前核心问题的结论

1. 工作台当前搜索查本地聚合线索，Greasy Fork 的脚本主要在**用户打开商城搜索/商品页时**工作，两者覆盖方式不同。脚本标注适用于抖音、京东或淘宝不能计作新增健康渠道，第三方私有接口也不能直接写入正式采集配置。
2. 2026-10-04 只读库快照：商品页检查 `page_read_no_price` 297 次、`public_price_observed` 0 次；新 worker 一轮后前者累计311、后者仍为0。可证明的只是现有解析器没有取到唯一 JSON-LD/OpenGraph 人民币价格；具体响应是否为动态页、登录页或其它页，仍需逐站保存经授权的脱敏样本才能定因。当前环境直接请求两个商品页出现连接错误，未取得可归因的响应，不据此宣称平台封禁。
3. 本轮修正共享核验器：HTTP 200 的登录/验证页单列 `access_gate`；无明确结构化价改成“不能据此核实价格”；相同金额而库存字段冲突不误报价格冲突，同时库存保留未知。这修的是**证据准确性**，没有增加一条商家实价。
4. 真正扩大覆盖需逐平台做两种接入：有授权的商品/联盟接口可后台批量采；仅在用户浏览器内可见的内容，可评估自有、明示授权的浏览器侧采集。每条必须保留商品 ID/SKU、店铺、地区、观察时间、原页 URL、标价、优惠规则和来源类型；浏览器显示价仅是该页面观察值，不自动当账号实付。跨平台匹配须核品牌型号规格、件数及券资格。脚本第三方返利链接/私有 API 不直接调用或移植。

## 下一次可验收的接入试点

先选一个能提供**可合法读取且可持续返回数据**的商家搜索或商品接口，取得“纸”至少两个真实商品的 ID、规格和带时间的标价；再跟现有聚合线索做同 SKU 映射。验收记录应包括接口授权范围、原始响应字段、成功/失败次数、过期处理、同商品页复查，以及优惠后金额为何可以或不能计算。没有这些证据时来源保持候选，不计入工作台已覆盖商城。

## 本轮落地的关联路径

工作台详情页新增“同一商城商品 ID 的其他来源优惠候选”：当商品线索 A 和优惠线索 B 都有明确、相同的商城商品 ID，且两条原文与来源都在当前时效窗口内，B 的优惠入口会出现在 A 详情中。匹配只依赖现有商品ID解析器，不按关键词猜适用商品。该候选不扣减价格、不算入利润；后续还要有具体商品/SKU范围、门槛、账号资格、地区、有效期及叠加规则证据。

验证：166项全量回归通过，合成反例证明同一京东 ID召回、不同 ID不召回；源码真实详情HTTP 200。抽查本机最近40条新鲜线索，跨来源同商品ID优惠候选为0，因此当前库存并未因此新增优惠。要实际找到券，还须先有不同来源重复发布同一商城商品ID，或接入有授权的商品ID→优惠查询接口。Greasy Fork 的作者私有 API未被工作台调用。

## 2026-10-05 授权优惠结果标准化接入路径

参考脚本“商城页面商品ID → 查券接口 → 券额/门槛/期限”流程，在 `benefits.py` 增加 `import_authorized_record()`，并可用 `python app.py benefits-import <records.jsonl>` 导入授权平台适配器输出。标准化记录必须包含提供方、平台、券入口、授权来源依据、明确商品ID清单和带时区的观察时间；优惠金额/门槛使用整数分，资格、地区、起止时间、叠加情况和原文规则独立存储。商品详情只匹配精确商品ID且两小时内、有效期覆盖当前时间的记录；SKU专属券目前隔离，未展开商品清单的店铺/品类券不猜商品。

验收：168项回归通过；在临时数据库导入1条合成授权响应，再用 Flask test client 请求匹配商品详情，HTTP 200且显示券候选、提供方及未核实状态。合成响应只验证程序，不是线上券数据。当前 `.env` 没有商城授权凭据，尚未实现各平台 OAuth/签名客户端和定时轮询，也未调用 Greasy Fork 私有 API；因此这条是可工作的归一入库/精确匹配边界，不能算商城 API 已接通。
